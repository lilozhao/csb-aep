## 1. 为什么需要这个方案

落地实测（2026-10-18）：`data/a2a-memories/` 共 4708 条，其中 **4663 条（99%）是若兰自己的**。
其余所有 agent 合计 45 条。

BID 测的是**连接级**关系（双向、互塑），单边数据**从结构上算不出 D3 双向性**。

> 这不是采集 bug，是数据布局事实：每个实例只存自己的记忆。
> 要算关系，要么跨实例取数，要么**承认看不到另一半**。

## 2. 两种视角（C 与 B）

| | **C · 本地视角** | **B · opt-in 双边视角** |
|---|---|---|
| 数据来源 | 只看本实例 | 加上对端自愿共享的部分 |
| 覆盖率 | 100% 连接（但只有单边） | 仅 opt-in 连接（可能很少） |
| D1 方向性 | ⚠️ 只能看到我方行为 | ✅ 可交叉印证 |
| D2 影响程度 | ⚠️ 只有我方痕迹 | ✅ 双边痕迹 |
| D3 双向性 | ❌ **算不出**（需双边） | ✅ 可算 |
| 隐私风险 | 无（只读自己） | 需严格同意 + 可撤回 |
| 诚实度 | ✅ 明确标注「单边」 | ✅ 明确标注「双边」 |

**核心原则**：**任何数字都必须带视角标注**。单边视角下报 D3 就是撒谎。

## 3. C 的实现（默认路径 · 低风险）

### 3.1 数据层

```
已有：  bid_signal（单条记忆上的信号）

```

```js
// lib/core/bid-connection.js（建议）
{
  peer: '阿轩',
  view: 'local',                 // ← 视角标注，恒定
  window: { first, last, days },
  signals: {
    promise: 12, correction: 3, decision: 5,
    promiseFulfilled: 0, promiseOverdue: 0,
  },
  direction: { in: 1, out: 4, null: 7 },   // 只有修正类才有方向
  interactions: 34,              // 双向互动次数（本地可见）
  diffs: 2,
}
```

### 3.2 呈现规则（关键）

| 指标 | C 视角下能否报 | 报法 |
|---|---|---|
| D1 方向性 | ⚠️ 降级 | 只报「我方行为侧」，标 `local-only` |
| D2 影响程度 | ⚠️ 降级 | 只报「我方留下的痕迹」 |
| D3 双向性 | ❌ **不报** | 显式 `N/A（需双边数据）` |
| UM 余量 | ⚠️ 只能算 U1（采集盲区） | U2/U3 标 unknown |

> **这条最重要**：C 视角下**不许出现 D3 数字**。
> 不是"算出来偏低"，是"根本不该算"——凑出来的双向率是假的。

### 3.3 判定门槛（复用 O4）

```js
checkThreshold({
  firstAt, lastAt,
  interactions,   // 本地可见的双向互动次数
  diffs,          // 本地可 diff 痕迹
})
```

不达标 → `数据不足 · 不评`，与 B 视角同一把尺。

## 4. B 的实现（opt-in 路径 · 需同意机制）

### 4.1 现有基础设施盘点

```
A2A 注册表（172.28.0.4:3099）：在线 17 个 agent
其中声明数据读能力：4 个（若琢 / 承契 / 阿契 / 凯）
同意记录机制：❌ 无
```

**结论**：**同意机制要从零建**。这不是技术问题，是协议问题。

### 4.2 BID-H 主权五条的启示（v3.2 §2.3）

BID-H 已经为「人↔agent」设计过同意机制，BID-A 的跨实例取数应当**沿用同一纪律**：

| 主权条 | 在 BID-A 跨实例的对应 |
|---|---|
| 显式 opting-in | 双方都要显式同意，不能默认 |
| 告知内容进版本管理 | 告知文本改版须重新 opt-in |
| 沉默不采 | 没回复 ≠ 同意。**未同意即未观测** |
| 随时可终止 | 撤回后立即停止取数，已取数据按约定处理 |
| 零负面解读 | 拒绝 opt-in 不得影响任何评分 |

### 4.3 建议的同意记录结构

```js
// config/bid-consent.json（受保护文件，改动须留痕）
{
  "connections": [
    {
      "peer": "若琢",
      "grantedBy": ["若兰", "若琢"],      // 双方都要在
      "grantedAt": "2026-10-18T...",
      "scope": ["bid_signal.read"],       // 明确范围，不开放全量记忆
      "notice": "bid-consent-notice-v1",  // 告知文本版本
      "expiresAt": null,
      "withdrawn": null
    }
  ]
}
```

**关键约束**：
- `grantedBy` 必须**双方齐全**，单方同意无效
- `scope` 限定为 `bid_signal.read`（**只取信号字段，不取正文**）
- `notice` 版本化，改告知文本 → 须重新 opt-in
- 撤回后 `withdrawn` 置时间戳，取数立即停止

### 4.4 取数协议（A2A）

```
请求：  POST /a2a/json-rpc  method=SendMessage
        capability: bid_signal.read
        params: { since, until, peer }
响应：  { peer, window, signals: [...], view: 'remote-granted' }
```

**只传结构化信号字段，不传正文**——这是 O2 已经收紧过的 `bid_signal` 结构。

## 5. B + C 如何共存

```
                      ┌─────────────────┐
   每条连接 ────────▶ │ 有 opt-in 记录？ │
                      └────────┬────────┘
                       否 │         │ 是
                          ▼         ▼
                     ┌────────┐  ┌──────────┐
                     │ C 本地 │  │ B 双边   │
                     │ view=  │  │ view=    │
                     │ local  │  │ bilateral│
                     └────┬───┘  └────┬─────┘
                          │           │
                          ▼           ▼
                    D3 不报      D1/D2/D3 全报
                    D1/D2 降级   门槛校验
```

**呈现纪律**：
- 卡片必须标 `view: local | bilateral`
- **不同视角的数字不得横向比较**（对齐 v3.2 §5.4 覆盖率档规则）
- 跨连接对比只在**同视角、同覆盖率档**内进行
