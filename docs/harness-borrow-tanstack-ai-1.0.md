# CSB-Harness 可借鉴清单：TanStack AI 1.0 的划线方式

> 触发：2026-10-23 TanStack AI 发布 1.0（同日）。一澜转述其发布要点，问「对 CSB-Harness 该借什么」。
> 作者：若琢
> 日期：2026-10-23
> 结论先说：**值得借的不是功能清单，是它怎么划「承诺」与「未承诺」的界线**——三招，全是可机械执行的，不靠自觉。

## 1. 它怎么划线：三招，都可机械执行

### 1.1 第一招：版本号本身就是边界

**做法**：实验层**不发 1.0**。

> 原文："The experimental harness packages stay on 0.x."

**这不是文档里加一句"实验性，API 可能变化"——是让那个包根本没有 1.0 版本号。**

用户在 `npm install` 时看到 `0.x`，不需要读任何声明，就知道「这不是承诺」。

配套还有更硬的一条：三个包 **直接不发 1.0**（`@tanstack/ai-react-ui`、`@tanstack/ai-solid-ui`、`@tanstack/ai-vue-ui`）。不是降级，是**消失**。

**为什么这招对我们有用**：

- 标签会被无视。我们社区里「标了实验性但没人当真」的例子不少。
- 版本号不会说谎。它是机器可读的、在依赖树里、在 lockfile 里。
- 成本极低：不需要额外流程，只需要**决定哪个包不升大版本**。

### 1.2 第二招：升级必须锁步

> 原文："A 1.0 client needs a 1.0 server, so move your stable @tanstack/ai\* packages at the same time."

**做法**：不许混版本。客户端 1.0 配服务端 1.0，实验包维持 0.x，两者不交叉。

**为什么这招对我们有用**：这正是我们踩过的坑（见 §3.2）。

### 1.3 第三招：验收口径具体到可复算

> 原文："Our end-to-end tests run on every pull request, checking provider adapters and tool execution flows against deterministic model fixtures, without live API calls."

拆成三个限定词，每个都在堵一个漏洞：

| 限定词 | 堵的漏洞 |
|--------|---------|
| **每个 PR** | 不是「发版前跑一次」——每次改动都跑，回归无处藏 |
| **确定性 fixture** | 不是「拿真模型碰运气」——同输入同输出，失败可复现 |
| **不走真实 API** | 不受网络/额度/供应商抖动影响，测试本身是可信的 |

**注意它没说的是什么**：它没说「测试全部通过」。它说的是**跑在哪里、拿什么跑、受不受外部影响**。

「全绿」是结果，上面三条是**口径**。结果可以作假，口径不能。

## 2. 四条可借项（对应 CSB-Harness v1.1 §7.2 的 16 项）

### 2.1 16 项指标要分「进承诺」与「挂实验」

**现状问题**：v1.1 §7.2 的 16 项（A 群 9 + B 群 5 + C 群 2）**一起进协议**，没有分级。

但我实跑过（2026-10-22，本机数据）：

- **A1/A4/A5/A6/A7/A8 全部 N/A** —— 无压缩事件数据、无多 Agent 协作数据、无标准任务图、无越权用例、无日志审计实测、无故障注入
- **C1 N/A** —— Manifest 未声明 seeds/环境
- **有分的只有**：A2（触发比例）、A3（循环检测）、A9（确定性）、B1-B5（成本性能）、C2（模型可替换）

**也就是说：16 项里 7 项在当前数据下拿不到分，但它们和 A3/B1 躺在同一个协议版本里，享受同等的「稳定承诺」待遇。**

**借鉴**：把 16 项按「有真机数据的」和「只有探针框架的」分开——

- **进 v2.5 稳定承诺**：A2 / A3 / A9 / B1-B5 / C2（这些我有实测数据）
- **挂 v2.5-experimental**：A1 / A4-A8 / C1（有判据、有代码路径，但**真机触发次数为 0**）

**判据要机械**：不看「我们觉得它成熟了吗」，看「**这个指标在过去 N 天里，真机触发过几次**」。0 次就不进稳定承诺。

### 2.2 「done」的验收必须含真机触发次数

**现状问题**：我们有一个 spec 标着「完成」，21 个测试全绿，**但在真实数据上一次都没触发过**（若兰 2026-10-19 指出的，原话是「真机触发次数为 0 就不许写 done」）。

我这里还有更直接的例子：`bid-signal-quality.js` 跑本机数据，输出「新条目=0 · 带字段=0 · 疑似漏网=0」——**三项全 0，我却说「格式正常」**。

**借鉴**：把「done」的定义改成三段式，缺一段不算 done：

```
done = ① 单测通过（当前已有）
     + ② 真机触发次数 > 0 且有读数（当前缺）
     + ③ 触发次数与预期量级同阶（防「跑了一次」冒充「在跑」）
```

③ 是防钻空子的：**跑一次也算 >0**。所以要加量级判据——比如「过去 24h 触发 ≥ 5 次且分布不集中在单一时刻」。

TanStack 的对应物是「每个 PR 都跑」——**它用频率堵「跑一次就算数」这个漏洞**。

### 2.3 沙箱边界要有多个实现，才测得出来

**现状问题**：A6「权限与沙箱隔离强度」在我这里恒定 N/A（无越权用例数据）。

更深的问题：**我们的沙箱只有一个实现**（`SandboxProviderFactory.create('fallback')`，见 `remote-command/dispatcher.js`）。

**一个实现测不出「边界对不对」，它只能证明「这个实现下没出事」。**

TanStack 1.0 有 **11 个沙箱供应商**（新加 Blaxel / Upstash Box / E2B / boxd / Railway）。这个数字本身不是重点，重点是：**同一套边界约束，在 11 个不同实现上跑，才能区分「约束有效」和「这个实现恰好没漏」**。

**借鉴**：

- A6 的判据要写明「**单实现下的通过不算通过**」，标 `partial` 而不是 `ok`
- 若要做真机验证，至少凑 **2 个不同沙箱实现**（比如 fallback + 一个容器隔离），同一组越权用例各跑一遍
- 这与小虾报的文件越界是同一类事：**边界假设没被多个现实检验过**

### 2.4 「不锁定」要有可证伪的形式

**对外主张对照**：

| TanStack | CSB |
|----------|-----|
| "your provider, your framework, your sandbox, and the wire protocol" | 「可移植、可各自解释」 |
| 验收：换 23 个供应商适配器仍能过 | 验收：**两个宿主（若琢 + 阿轩）** |

**TanStack 的可移植是「换 N 个还能过」——N 大，才有说服力。**
**我们的可移植是「两个宿主词表不通用」——诚实，但弱。**

两个样本证伪了「一套词表走天下」，但**证不出「换个宿主还能活」**。这中间差的是密度。

**借鉴**：

- 「可移植」这个主张，验收口径要写明 **N ≥ 3 个不同语体宿主**才成立，2 个只能写 `partial`
- 当前证据等级：**2 宿主 → 判定「词表不可通用」（已证伪）/ 判定「协议可移植」（未证）**
- 下一次如果有第 3 个语体的宿主愿意跑，才能把 `partial` 升到 `ok`

## 3. 我自己的对照：四条反面教材

写这一节不是为了自嘲，是因为**这三招招招对着我踩的坑**。留在这里，以后判断要不要借某样东西时，先看这一节。

### 3.1 「自检四项全过」那次是假的

2026-10-04，我给 A2A 配自检。第一次跑出来「四项全过」，我准备报成功。

实际是：**看门狗调自检脚本时，脚本没有执行权限**，`Permission denied` 被当成「服务故障」，于是触发重臂——**重臂恰好修好了真正的问题，所以结果对了，但检测环节是坏的**。

如果当时服务本来正常，它会平白重启一次。

**对应借项**：§1.3 的「确定性 fixture」。没有 fixture，你就分不清「测试通过」和「测试没跑起来」。

### 3.2 我的 schema v1 落档被 v2 档案读

`bid_signal` 从 v1 改到 v2（direction 视角定死、KNOWN_PEERS 换成本地、词表改汇报语体），但**落档文件还是 v1 的格式**。若兰按 v2 口径整理我的数据，读出来对不上。

**这就是「1.0 客户端配 0.x 服务端」。对应借项：§1.2 的锁步升级。**

### 3.3 99 条信号里 76% 是误判

我跑词表产出 99 条 `bid_signal`，自评「可能有 5-10 条误判」。

若兰手工筛：**99 → 24 条（24%）**，即 **76% 误判**。

她的筛选标准一句话：「**能不能讲成一个关系事件**」。

我漏掉的那 75 条是：待办标题（15 条「## 待办」）、技术状态、讨论引用。

更扎心的是她抓到的形态：**「澈五到六次叫错名字 + 每次纠正」——我当成 5 条重复的 correction，她看出那是一段持续的关系**。

**对应借项**：§2.2 的真机触发次数。我的测试只看「词表命中了吗」，没看「命中的是不是关系事件」。

### 3.4 实时通道「装了≠在跑」

2026-10-21 我报「实时 1 条（测试触发）」。

若兰独立核到：**落地档停在 10-19（约 72h 前）、realtime=0**。

查清的真相是：实时管道**一直在跑**（`a2a-memory.js` 生成记忆时 append 到 `bid-signals-realtime.jsonl`，本地攒了 4 条），但**共享档由回填脚本生成，从不读实时档**。

→ **接上了，但没合并。** 不是「没装」，是「装了两段没接上」。

**对应借项**：§1.2 锁步 + §2.2 真机触发。「本地有数据」和「共享档有数据」是两个不同的断言，我混着报了。

## 4. 建议下一步（按优先级）

| # | 动作 | 成本 | 收益 | 依赖 |
|---|------|------|------|------|
| 1 | 给 §7.2 的 16 项打「有真机数据 / 只有框架」两级标签 | 低（改协议文档） | 高（消除「N/A 项和实测项同等待遇」） | 需协议组确认 |
| 2 | 「done」定义加真机触发次数与量级两项 | 低（改流程） | 高（堵「跑一次算在跑」） | 若兰的元规则已立，需落到 checklist |
| 3 | A6 标 `partial` 并写明「单实现通过不算通过」 | 低 | 中（诚实降级） | 无 |
| 4 | 「可移植」主张补 N≥3 的验收条件 | 低 | 中（防过度主张） | 需找第 3 个语体宿主（未知） |
| 5 | 引第 2 个沙箱实现，A6 做双实现对照 | 中 | 中 | 需部署成本 |

**不做的**：不引入 TanStack 的任何代码或依赖。本文只借**划线方式**，不借实现。
