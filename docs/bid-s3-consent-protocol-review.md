## 1. 同意机制：实现已定，条文待审

实现遵循 BID-H 主权五条的移植，代码层面已写死：

| 主权条 | 代码落点 | 行为 |
|---|---|---|
| 显式 opt-in | `grant()` | `grantedBy` < 2 方直接抛错 |
| 沉默不采 | `checkConsent()` | 无记录 / 文件损坏 ⇒ 不允许（安全失败） |
| 告知版本化 | `CURRENT_NOTICE` 比对 | 版本不符 ⇒ 视为未同意 |
| 随时可终止 | `withdraw()` | 置时间戳，`checkConsent()` 立即 false |
| 零负面解读 | —— | 拒绝/撤回不进任何评分输入 |

### 1.1 待评审条文（Q 系列）

**Q-S3-1｜撤回后删除窗口 72h 是否合适？**
当前：撤回 → 立停取数 → **72h 内**删除原始信号副本与聚合记录 → `purgedAt`。删不掉的进 `undeletable` 如实报告。
反方意见：关系数据敏感，72h 偏长；正方：需跨实例核销、留痕核对。
若兰倾向：**保持 72h**，但要求 **24h 内先做「隔离」（不再被任何计算读到）**，48h 内完成删除。→ 需评审确认是否采纳「两段式」。

**Q-S3-2｜单方撤回能否生效？**
当前：`withdraw(peer, by)` **任一方**都能撤回（撤回权不收窄）。
需确认：一方撤回后，另一方是否需被通知？建议 **必须通知**（否则「以为还在采」）。

**Q-S3-3｜`purge` 是人工确认还是可自动？**
当前：`purgePlan()` 只出清单，删除须人工确认（不可逆）。
风险：无人值守时会拖过期限。建议 **超期 24h 自动告警**（不自动删）。

**Q-S3-4｜告知文本改版 ⇒ 全部重新 opt-in，是否太重？**
当前：`notice` 版本不符即失效（全量重签）。
反方：错别字级改动也要重签，成本高。
建议：**语义变更才升版本号**，措辞/排版变更记 patch、不触发重签——但这与「写死」的原则冲突，需评审定。

## 2. 取数协议（S4 · 全新设计，本文核心）

### 2.1 请求形状

```
POST /a2a/json-rpc
{
  "jsonrpc": "2.0",
  "method": "SendMessage",
  "id": "bid-fetch-<uuid>",
  "params": {
    "message": {
      "role": "user",
      "messageId": "bid-fetch-<uuid>",
      "parts": [{ "type": "text", "text": "…人可读说明…" }],
      "metadata": {
        "capability": "bid_signal.read",
        "sender": "若兰",
        "params": { "since": "2026-10-01", "until": "2026-10-19", "peer": "若兰" }
      }
    }
  }
}
```

### 2.2 响应形状（**只回信号字段，绝不回正文**）

```json
{
  "peer": "若琢", "view": "remote-granted",
  "window": { "since": "...", "until": "..." },
  "consent": { "notice": "bid-a-consent-notice-v1", "grantedAt": "..." },
  "signals": [
    { "kind": "promise", "peer": "若兰", "direction": "out",
      "state": "fulfilled", "origin": "realtime", "at": "2026-10-16" }
  ],
  "receipt": { "count": 12, "sha256": "…", "generatedAt": "…" }
}
```

**白名单字段写死**：`kind / peer / direction / state / origin / at`
其余一律**不传**（含 content、title、tags、id、文件路径）。

### 2.3 待评审条文（Q 系列）

**Q-S4-1｜`at` 精确到日还是到秒？**
建议：**到日**（`YYYY-MM-DD`）。到秒会形成行为节律画像，超出「信号类别」的必要范围。

**Q-S4-2｜跨实例传输走内网还是公网？**
内网（同 Docker 网络）建议明文 + 注册表鉴别；公网实例须 TLS。**需确认是否有公网试点计划**。

**Q-S4-3｜响应可否缓存？**
建议：**不缓存**，每次现算。缓存会产生「撤回后仍可读到旧值」的漏洞。

**Q-S4-4｜接收方如何验证发送方身份？**
现有 A2A 只有 `sender` 字段自报。建议：**以注册表登记的身份为准**（防冒名），未登记的 sender 一律拒。

**Q-S4-5｜取数频率上限？**
建议：**每连接每 24h ≤ 1 次全量**，增量另计。防止高频轮询变相形成监控。

## 3. 双边聚合（S4 后半）

```
本地 signals（C 视角，逐条）  +  远端 signals（B 视角，可选）
                    ↓
              配对（按 peer + kind + 时间窗）
                    ↓
          D3 双向性 = 双向都出现的信号对 / 总信号对
```

**必须同时报的三件事**（否则数字不可解释）：
1. `view: bilateral`
2. `coverage`: 双边覆盖的信号占比（远端可能只回了一部分）
3. `unmatched`: 无法配对的信号数（本地有远端无 / 远端有本地无）

> **纪律**：`coverage` < 50% 时 **D3 仍报 N/A**——配对率太低算出来的双向率没有意义。
