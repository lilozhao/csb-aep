# CSB BadCase 库 v0.1

> **来源**：知微《CSB-AEP × QCA 评测 Loop 借鉴备忘 v2》第五节「业务 BadCase 库：从社区真实事故沉淀用例，别人抄不走」。

> **脱敏边界**：只留结构，不留原文；不出现身份标识、网络地址、完整业务原文。

## 为什么建这个库

「别人抄得走题面，抄不走结构。」

同一个错误如果在两处独立发生，它就不是某个人的疏忽——是**机制缺了一格**。这个库收的是**缺的那一格**，不是犯错的人。

## BC-001 · 样本内满分 → held-out 崩盘

| 项 | 内容 |
|---|---|
| **ID** | BC-001 |
| **严重度** | S2-严重（不损坏数据，但会导致带病协议被放行） |
| **状态** | closed（已拦截，判据返工中） |
| **日期** | 2026-10-23 |

### 场景
验证「关系事件」提取判据是否成立，决定是否纳入协议（P-16 候选）。**判据设计者 = 判据验证者（同一人）**，若判据有误未被发现，将作为协议条款落地，影响全部接入实例。

### 触发条件
用人工标注样本调判据，**调完立刻在同一批样本上评测**。
- **结构性缺陷**：调参与评测使用同一集合 → 判据记住了样本特征，而非学到判别规则
- **为什么没被察觉**：设计者看到「过判 0、召回 100%」即认为达标
- **可复现性**：任何「无独立留出集」的判据/规则/提示词调优流程都会复现

### 期望 vs 实际

| | 样本内 | held-out |
|---|---|---|
| 集合大小 | 33 | 122 |
| 集合来源 | 人工标注，判据调参时反复参照 | 天然留出：原始池 126 − 4 重叠，从未参与调参 |
| 过判（FP） | **0** | **3**（V1=43% / V2=25% / V3=43%） |
| 召回 | 100% | 4/4 命中项中真关系 |

**唯一变量是评测集合的划分**——同一份判据代码。

### 根因
- **主因**：评测集合划分缺失——调参集与评测集重合，且该事实**未被记录在任何 baseline 元数据中**
- **次因**：判据设计者与验证者同为一人，缺少异构复核
- **模式**：「没发现问题」被当作「有证据证明没问题」——**三态语义中把 🟡 误判为 🟢**
- **泛化**：不是某条判据写错了，而是**流程缺一格**：baseline 未声明它在哪个集合上成立

**三条过判共享同一形状**——全部是「关于事件的话」而非「事件本身」：动作清单 / 教训反思 / 引用他人话语。

### 修复
**立即**：P-16 判为「暂不开 · 判据返工」——不带病进入协议层。

**流程修复**：
1. baseline 必须声明评测集合划分（`in-sample` / `held-out` / `online`），**跨集合不得比较为「未退步」**
2. **unknown 比例本身作为 KPI**：仅当 unknown 比例不上升时，通过率上升才可计为进步
3. 判据设计者须**先交出自己在 held-out 上的过判率**，方有权给出绿灯

**设计修复**：判据从「可指称性」升级为「**可指称性 + 事件性**」，须能区分 事件 / 列举 / 反思 / 转述 四种形态。

**没做的事**：未修改判据代码——因为重新调参会**再次污染同一批样本**，需先扩池 ≥50 条独立负例。

### 回归
- **回归套件**：`bid-p16-probe.js` 的 held-out 段自动跑，过判率作为回归指标
- **验收标准**：独立 held-out 上过判率 ≤ 5%，且 unknown 比例不高于基线
- **状态**：open — 等待扩池与判据返工

### 复现
```bash
node csb-aep/scripts/bid-p16-probe.js
```
输入：`goldset-ruozhuo-v0.3.json`（33 条样本内）· `goldset-p16-heldout-v0.1.json`（7 条 held-out 标注）· `bid-signals-ruozhuo.json`（126 条原始池）
提交：`f280223`

### 教训
1. 一个漂亮的全绿分数，**在不知道它是在哪个集合上量的之前，等于没有信息**
2. 最危险的不是判据错，**是判据在错误的集合上对**
3. 三条同形状的失败，指向的是同一个机制缺口，**不是三次偶然**
