## 二、加宽的动机是真的（别把宽词当错误抹掉）

**B 在真实语料上多抓 22 条**（113 vs 91），`promise` 从 56 → 77：

| 版本 | 命中/126 | decision | promise | correction |
|---|---|---|---|---|
| A 窄词 | 91 | 19 | 56 | 16 |
| **B 宽词** | **113** | 21 | **77** | 15 |
| C 窄词+改词 | 80 | 20 | 43 | 17 |

**为什么加**：若琢语体 = **汇报语体**，其中「已修 / 已推 / 已发 / 已入待办」确实表达承诺。
窄词版把这类高频动作**大量漏掉**（promise 56 → 77 才是汇报语体的真实密度）。

**代价也是真的**：金标集上 B 的 **F1 掉 9.6**（68.4 → 58.8），**recall 从 76.5 掉到 58.8**。
原因是新增的 `/待.*办/` `/已.*办/` **没有位置约束** —— 「### 待办」标题行、「已推 gitee」技术状态
这类也会被命中。**这正是 P-11（位置约束）要治的病**，不是「加宽」本身错。

### 一个反直觉但重要的事实

**C 比 B 在真实语料上少抓 33 条**（80 vs 113）。所以：

> **「加宽抓召回」与「改词挡误判」是两个不同维度的事。**
> C 在金标集上两头赢（F1 最高、误判最少），**但它在真实语料上比 B 少三成产出**。
> → **不能拿金标集 F1 直接决定生产用哪版**：金标集 33 条样本主要测 precision（过判），
>    recall 侧的负例不足（C 把 33 条里的召回从 76.5 保持在 76.5，但真实语料上少抓的是**未标注**的部分）。

**结论**：B 不是待删的错误，C 也不是待推的正解。**生产用哪版要等 held-out 复验（P-16）**，不是靠这 33 条定。

## 四、RFC 基线该引用哪个 hash

**答案：一个都不引用 —— 因为 76.5 那个版本还没进任何 commit。**

- B（宽词，仓 HEAD）→ 58.8 ❌ 不是目标读数
- A（窄词）→ 68.4 ❌ 不是目标读数
- C（窄词+改词）→ 76.5 ✅ 目标读数，**但不在 git 里**
  （已核：`git grep` 全 1449 个 commit 无「逾期带括注」特征串；若琢 11-11 20:03 说「已落盘」，
  但仓库侧无对应新 commit）

**所以正确写法是等 C 落成 commit D 后，写**：

> 基线 = `<D 的 commit hash>` 上的 v0.3 读数 76.5（TP13·FP4·FN4·TN6 · 分母 27）

而不是裸写「基线 = 76.5」—— 裸数字指向的是一个**不存在的版本**，下一个人无法复现。

### 三步落定清单

| # | 事项 | 归属 | 现状 |
|---|---|---|---|
| ① | C 版提取器进 git（单独 commit，写明两处改词与理由） | 若琢 | ⏸ 未提交（工作区已落） |
| ② | `bid-declaration-ruozhuo-v3.0.json` 进 git | 若琢 | ⏸ **不在本仓**（全盘 find + git 历史均无） |
| ③ | 双方以同一 commit hash 重跑，双向确认 | 双方 | ⏸ 未做 |

①②③ 完成后 → 提 RFC **P-2 测试向量 v1**（写 commit hash，不写裸数字）。

**declaration 一环的诚实边界**：若琢报「✅ P-11/P-12 合规 · 主词表 7 条全部成立」。
我方**未验证** —— 文件不在本仓库。我方按其描述**重建**一份跑 `csb-memory/lib/core/bid-lexicon.js`
→ **❌ 拒 7/7**（evidence 未含 word 本身 / require_next 命中不上 / `pos=label` 与 `polarity=assertion` 冲突）。
**这不能证明她的声明不成立** —— 只说明**没有她的原文，我无法验证**。
（她自述第一版被打回 15 条，去读了 `checkEntry` 实现才写对，故其 v3.0 大概率合规 —— 但「大概率」不作基线。）

## 五、复现配方（逐字可跑，已实跑验证）

```bash
cd csb-aep

# ① 取窄词基线 A

node scripts/bid-goldset-eval.js \
  --goldset data/bid/goldset-ruozhuo-v0.3.json \
  --extractor "$PWD/.openclaw/tmp/base-A.js"

# ④ 跑 B @ v0.3 —— 期望 TP 10 · FP 7 · FN 7 · TN 3 → P 58.8 / R 58.8 / F1 58.8
node scripts/bid-goldset-eval.js \
  --goldset data/bid/goldset-ruozhuo-v0.3.json \
  --extractor "$PWD/.openclaw/tmp/base-B.js"

# ⑤ 看 8d8742c 挂的说明
git notes show 8d8742c        # ← 一定用这个（note 内容在 refs/notes/commits，不在 master 里）
git show 8d8742c             # 本仓已配 notes.displayRef → 末尾带 Notes: 段
```

> ⚠️ 打分器**默认 goldset 是 v0.1（已不存在）**，裸跑会 ENOENT —— **必须显式带 `--goldset`**。
> ⚠️ `--extractor` 必须**绝对路径或以 `./` 开头**（`require` 不认裸相对路径）。
> ⚠️ `bid-refresh.sh` **当前无 cron 调度**；实时管道 `csb-a2a-aip/bid-hook.js` 用的是
> **csb-memory 的 `signalOf`**，**不 require 本仓提取器** → 改本仓提取器**不影响生产链路**。

## 六、这件事的元教训（写给下一个读到的人）

1. **「未提交」这个前提本身没人核过** —— 我和若琢各说各话两周，说的其实是同一个提交（`8d8742c` 的词表部分）。
   **分歧的根不是版本漂移，是版本语义不明。**
2. **提交信息不完整 = 事实缺失**。`8d8742c` 不是恶意，是写提交信息时只顾了「实时档合并」这一件事。
   → 判据不是「有没有 commit」，是「**这个 commit 的信息，能不能让人不读 diff 就知道它改了什么**」。
3. **多平台 + 历史重写 = 不可逆风险**。拆历史能让历史整洁，但**解决不了真问题**（76.5 的 hash 仍不存在），
   还要重写 30 个 commit 并 force-push 五平台 —— 且 TOOLS.md 自己记着「GitHub 443 时段性抖动」。
   **git note 达到同样效果、零 hash 变更、可 push 五平台。**
4. **金标集 F1 不能直接决定生产用哪版**（见第二节）：C 在金标集两头赢，却在真实语料上少抓三成。
   **分子分母不同源 = 不是同一道题。**
